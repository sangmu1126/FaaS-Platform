# Public E2E Function Completion Test — 2026-08-09

## Purpose

This test separates completed function throughput from the previously documented
asynchronous request-acceptance throughput. A request counts as successful only
when the public API returns a successful Worker execution result.

## Path and environment

```text
k6 2.1.0 on a local macOS client
  -> CloudFront HTTPS
  -> ALB
  -> authenticated Node.js BFF
  -> Controller
  -> SQS
  -> one t3.small Worker
  -> Python Docker container
  -> synchronous result returned to k6
```

- Region: `ap-northeast-2`
- Worker ASG during the tests: one `InService` instance
- Function: `Fibonacci(25)` followed by a 500 ms sleep
- Runtime / allocation: Python / 128 MB
- Workload: constant-arrival-rate for 30 seconds
- Success condition: HTTP 200 and result `status == "SUCCESS"`
- Raw and summary data: JSON files beside this report

## Results

| Offered rate | Completed | Dropped before start | Function success | Observed completion rate | Handler p95 | Worker-internal p95 | Public E2E p95 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 RPS | 31 | 0 | 100% | 0.946 RPS | 500.67 ms | 1.54 s | 3.72 s |
| 2 RPS | 56 | 5 | 100% | 1.446 RPS | 503.29 ms | 4.43 s | 9.33 s |
| 3 RPS | 71 | 20 | 100% | 1.451 RPS | 503.59 ms | 9.33 s | 18.75 s |

The observed completion rate uses k6's full run time, including graceful drain.
`dropped_iterations` means k6 could not start all scheduled iterations within
the configured VU limit; it is not a function execution failure.

## Cross-check

After all runs, the Worker Prometheus endpoint reported:

```text
worker_jobs_processed_total{runtime="python",status="success"} 178
worker_active_jobs 0
```

The count exactly matches one preflight execution plus all k6 completions:
`1 + 19 + 71 + 31 + 56 = 178`. SQS reported zero visible and zero in-flight
messages after the test.

## Interpretation

- One Worker sustained the 1 RPS workload with no dropped iterations or failures.
- At 2 and 3 offered RPS, completion throughput converged near 1.45 RPS while
  queueing latency increased sharply.
- Handler duration remained near 500 ms at every load level. The increased
  latency therefore came from platform queueing and execution orchestration,
  not from the user handler.
- These are public synchronous E2E results. They are not comparable to the old
  520 RPS figure, which measured asynchronous request acceptance on localhost.
- The 30-second runs did not trigger a Worker scale-out; they do not prove ASG
  scaling efficiency or multi-Worker throughput.

## Baseline note

The `1vu-baseline` files came from an initial run where the environment variable
name `K6_DURATION` unintentionally overrode the scripted scenario. The files
were retained under an accurate name as a closed-loop one-VU baseline, but they
are excluded from the primary constant-arrival-rate comparison above.
